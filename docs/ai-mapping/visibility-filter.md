# Фильтр видимости атрибутов перед LLM

Дата: 2026-10-08. Ветка: `AIMappingAssistant`. Изменение реализовано на сервере.

## Задача и фактические правила

Пользователь предложил сократить кандидатов по видимости атрибутов для категории. Ранее AI учитывал только видимые группы и применимые типы объектов.

У атрибута `visible` содержит внутренние ID узлов каталога OpenPIM, а не ID категории маркетплейса. Видимость наследуется по пути узла: доступность на предке действует на потомков. При наличии `relations` обычные атрибуты могут проверяться по путям источников связи, а не по пути товара. Тип 9 и опция `standard_attribute=true` используют путь товара.

Обычный dropdown маркетплейсного редактора сейчас содержит широкий список PIM-атрибутов и сам не фильтрует его по категории. Поэтому новое поведение AI основано на правилах видимости атрибутов в редакторе объектов и настройках сохранённого маппинга, а не на буквальном копировании списка dropdown.

## Реализованный алгоритм

1. Берём сохранённые `category.visible`, `category.visibleRelation` и применимые типы. Несохранённые изменения этих настроек в браузере в запрос не передаются.
2. В пределах текущего tenant загружаем выбранные корни каталога и их активные поддеревья. Отсутствующие или некорректные корни вызывают ошибку до обращения к модели.
3. Если указана связь, добавляем пути остальных активных источников на этой же связи у товаров, связанных с выбранными источниками. Это сохраняет доступность атрибутов у товара, имеющего несколько входящих категорийных связей.
4. Один раз строим множество ID из всех полученных путей, включая предков.
5. До ранжирования кандидатов проверяем `attr.visible`.
6. Атрибут с явно пустой видимостью исключается, когда известен контекст категории.
7. В связи с категориями фильтруем обычные атрибуты, использующие исключительно эту же связь. Для прямого дерева фильтруем атрибуты, использующие путь товара.
8. Атрибуты других связей, нескольких разных связей и стандартные поля товара при категорийной связи сохраняем: по этому контексту нельзя доказать их недоступность.
9. Если у маппинга нет `visible` или нужный контекст отсутствует, сохраняем прежний отбор по группам и типам, без угадывания категории по названию.

Фильтр сокращает множество потенциально применимых атрибутов; он не проверяет заполненность значений у конкретного товара и не заменяет права доступа к отдельному объекту. Дополнительные связи неизвестного домена сохранены намеренно, поэтому часть кандидатов других каталогов остаётся.

SQL использует связанные параметры и ограничения tenant для узлов и обеих сторон связей; удалённые источники и связи исключаются. Пути и связи не передаются LLM: провайдер получает только прежние разрешённые описательные поля оставшихся кандидатов.

## Результат на Kuppersberg

Сравнение выполнено на прежних трёх категориях `ym`, без изменения базы и сохранённого маппинга. За основу взят [первый прогон](kuppersberg-first-run.md).

| Категория | Кандидатов до топ-30 без фильтра | С фильтром | Исключено | Прежних соответствий в топ-30 |
| --- | ---: | ---: | ---: | ---: |
| Комбайны и измельчители, 90601 | 5099 | 4000 | 1099 (21,6%) | 3/5 → 3/5 |
| Винные шкафы, 15450095 | 5099 | 4004 | 1095 (21,5%) | 5/5 → 5/5 |
| Сковороды-гриль, 61377314 | 5099 | 3994 | 1105 (21,7%) | 2/5 → 2/5 |

Множество кандидатов уменьшилось примерно на 22%, но покрытие существующих соответствий топ-30 осталось 10/15. Фильтр не устранил ограничения лексического ранжирования.

Дополнительно вызвали модель для первых пяти характеристик категории 90601: 5 предложений, 3 совпадения с существующим маппингом, 8,863 с. Модель выбрала общий `mv862` для «Типа» с предупреждением о несовместимости словаря и строкового типа. Предметная проверка по-прежнему необходима.

После проверки кода добавили обработку стандартных атрибутов и нескольких входящих источников. Повторный локальный анализ подтвердил прежние размеры выборки и совпадение всех пяти списков кандидатов с использованными в AI-прогоне. Полный новый LLM-прогон трёх категорий не выполнялся. Суммарно в ранее согласованном эксперименте отправлено 26 характеристик из разрешённых 30.

## Проверки

- Новые тесты сначала воспроизвели отсутствие фильтра, затем прошли после реализации.
- Проверены категория и предки, поддеревья выбранных корней, несколько путей, точные ID без совпадения по префиксу.
- Проверены другие связи, несколько связей, стандартные атрибуты и отсутствие контекста.
- Проверена передача tenant и relation ID в загрузчик, отсутствие корней и некорректные пути.
- SQL-тест на синтетических `VALUES` в `READ ONLY` проверяет несколько источников, чужой tenant и удалённые связи; реальные таблицы в этом тесте затенены CTE.
- Полный запуск: 31 тест, 0 ошибок/пропусков. TypeScript-проверка прошла.
- Клиентские файлы этого этапа не менялись; браузерный прогон нового серверного фильтра отдельно не выполнен.

Команда проверки из `server`:

```powershell
node -r ts-node/register/transpile-only --test tests/ai-mapping.test.cjs tests/ai-mapping-access.test.cjs tests/ai-mapping-visibility-query.test.cjs
npx tsc --noEmit
```

SQL-тест требует окружения Kuppersberg; при другом имени базы он пропускается. Транспортные тесты используют локальный фиктивный провайдер.

## Артефакты

- `src/channels/ai/access.ts`: загрузка контекста сохранённого маппинга.
- `src/channels/ai/visibility.ts`: SQL загрузки путей, общий для сервера и диагностического скрипта.

Режим `--metadata-only --visibility` скрипта оценки выполняет локальный отбор и получение метаданных Яндекс Маркета, без обращения к модели. Для следующих AI-повторов с фильтром предусмотрен отдельный файл `kuppersberg-visibility-evaluation-repeat.json`, чтобы не перезаписывать полный отчёт.

## Следующий вывод

Фильтр видимости полезен как первый этап уменьшения выборки, но недостаточен для категорийных «Типа» и «Материала». Следующий эксперимент — категорийное ранжирование оставшихся кандидатов. Сравнивать нужно отдельно сокращение множества, попадание проверенного правильного кандидата в топ-30 и правильность выбора модели. Существующий маппинг ещё не является вручную проверенным эталоном.

## Обновление 2026-10-08: целевые пути товаров

Описанный выше первоначальный фильтр дополнен отдельными targetPaths: обычные, стандартные и поля типа 9 при выборе категории через связь теперь проверяются по мастер-каталогу. Исходные пути и альтернативные источники остаются для атрибутов выбранной связи. Для других областей или отсутствующих товаров сохраняется неизвестный контекст. Реализация, ограничения и результаты повторного теста: [видимость товаров и поиск](target-visibility-and-search.md).
